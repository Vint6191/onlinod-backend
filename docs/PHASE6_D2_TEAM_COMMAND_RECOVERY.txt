2. СЕРВЕРНЫЙ КОНТРАКТ

Новые POST /api/team/commands/v2 и /api/team/commands/v2/cancel.
Agency, user, device берутся только из admitted auth. Envelope строгий:
commandId UUID, action, targetId, payload, optional actorProof. UUID приводится
к нижнему регистру. Payload проверяется отдельной строгой схемой каждого action;
expectedRevision смен сохранён, обязательные поля/ограничения прежних команд
сохранены. Команда и повтор одного намерения отличаются только replayed.
Proof не является частью fingerprint и вычисляется заново, когда нужен.

15 canonical actions:
member.update / member.status / member.remove;
invitation.create / invitation.reissue / invitation.revoke;
role.create / role.update / role.access / role.permission / role.reset / role.delete;
shift.create / shift.update / shift.cancel.
Старые 16 Team Administration writers с aliases и 3 Schedule writers возвращают
410 TEAM_COMMAND_V2_REQUIRED до доменного эффекта. GET и ownership transfer
сохранены. Старый Backend не знает /commands/v2 и потому не сможет молча
исполнить новую команду без receipt. Старый Desktop на новом Backend должен
обновиться; атомарная установка связанных Backend/Desktop обязательна в плане
развёртывания. До проверки сборки пакет не рекомендован к установке.

TeamMutationReceipt — новая отдельная таблица, deterministic primary key
sha256(agency, user, commandId), action/target/fingerprint, COMMITTED|ABANDONED,
secret-free JSON result и authorizationScope, createdAt. Отсутствуют plaintext
invitation token/URL, owner proof, access/refresh tokens. Никакого TTL, который
мог бы превратить старую команду в новую: receipt живёт до удаления agency.
Максимумы result и scope по 2 MiB, CHECK в БД. Это ограничение размера одной
записи, не обещание фиксированного суммарного диска при бесконечном числе команд.
Lookup только по PK, не скан истории команд. Результат нормализован как JSON,
включая даты, поэтому первый ответ и повтор имеют один представимый контракт.

Одна root Serializable transaction существующего db-commit-kernel:
command-only advisory mutex -> receipt lookup -> branch-specific current authority
-> доменная операция -> обязательный аудит -> receipt -> commit.
Никаких network sends внутри callback. Существующие domain lock orders
Agency/Role/Creator/User/Member не заменены ранним Member-lock. Новый mutex
берётся только этим семейством до остальных блокировок. Team Administration
присоединяется через kernel-issued commitContext. Schedule теперь аналогично
владеет всем command root/join, включая audit(required:true). Hints Team Admin
по-прежнему отложены до успешного commit; rollback их не публикует.

При replay проверяются текущие active User/Member, permission action, исходный
и текущий creator scope, broad-scope/OWNER ограничения, делегирование роли и
доступные powers возвращаемой роли. Для смен также проверяются analytics view
и product billing. Ответ не выдаётся только потому, что UUID уже существует.
Сам SELECT receipt предшествует проверке scope, но данные не возвращаются до
проверки current authority. Changed fingerprint -> 409 без доменного эффекта.
Уже выполненная смена повторяется из receipt раньше проверки старой revision;
новая команда с устаревшей revision всё ещё отклоняется.

Cancel не означает откат выполненного действия. Сервер под тем же mutex:
- если команда не выполнилась — сохраняет ABANDONED tombstone;
- если COMMITTED — сообщает alreadyCommitted, не отменяя результат;
- повтор cancellation безопасен; задержавшийся execute после ABANDONED запрещён.
Для отказа от своего pending требуется актуальный active actor/agency, но не
сохранение прежних бизнес-permissions: это позволяет убрать зависшее действие
после отзыва права, не открывая содержимое прежнего результата.

Восстановление приглашения: token выводится HMAC-SHA256 из существующего
JWT_SECRET и отдельного cryptographic domain + agency/user/command/fingerprint.
В AgencyInvitation остаётся только привычный tokenHash. Receipt хранит профиль
приглашения. Повтор возвращает ссылку лишь если hash по-прежнему совпадает,
приглашение не claimed/revoked/expired (DB clock). Перевыпуск другим намерением,
истечение, отзыв, claim или смена JWT_SECRET -> успешное подтверждение прежнего
действия с linkAvailable:false и null token/url; новый invite/token не создаётся.
Ротация JWT_SECRET отключает recovery старых ссылок и не продлевает/не отзывает
их сама. Новая environment-переменная или plaintext secret cache не введены.

Cleanup новой таблицы добавлен в существующий bounded agency non-FK purge и
residual inventory. Для receipt используется LIMIT + ORDER BY id через индекс
(agencyId,id); прежние механизмы других таблиц не переписываются. Нормальные
member/creator removals не стирают receipt и не оживляют старый command ID.
Серверный переезд переписки и полная Phase7 purge остаются отдельными узлами.

3. DESKTOP: НАМЕРЕНИЕ, ДОСТАВКА ОТВЕТА И RECOVERY

Один shared TeamCommandTransport в Main обслуживает оба раздела. Все 15
продуктовых вызовов переведены на него; ownership transfer остаётся отдельным.
До первого HTTP-запроса durable AtomicJsonStore записывает UUID и точное
нормализованное намерение. Namespace: apiBase + userId + activeAgencyId.
Authorization incarnation дополнительно проверяется после ожидания owner proof
и после HTTP; смена аккаунта не может представить поздний ответ другому actor.
Relogin того же principal позволяет явное recovery с актуальным разрешением.

Файл team-command-pending-v1.json: не более 32 unresolved intentions, общий
serialized размер <=4 MiB, payload <=1 MiB. Нет actorProof/auth tokens,
invitation tokens, URLs или response cache. Ошибка записи ДО HTTP блокирует
отправку; ошибка чтения/повреждение не заменяется пустым журналом. Backup-only
окно Windows replacement восстанавливает старый файл, сохраняя UUID.
Это защита process restart, не отдельное доказательство power-loss/storage
hardware durability; AtomicJsonStore использует существующий fsync+rename.

Повтор того же action/target/payload получает прежний UUID. Одновременные
одинаковые попытки объединяются. Пока результат не разобран, другая команда
для того же resource family/target блокируется; новый payload нельзя отправить
под старым ID. New create имеет собственный family create-slot. Ограничение
журнала никогда не вытесняет старое неопределённое намерение автоматически.
Ошибки сети/401/5xx и business rejection не удаляют ID без подтверждения.
Пользователь может явно отменить pending серверным tombstone.

Main сохраняет receipt-delivered state, но не забывает ID после HTTP success:
сначала Renderer должен получить ответ и отправить acknowledge. Потеря Main->
Renderer IPC reply/перезапуск Renderer до acknowledge сохраняет recovery.
Потеря ответа самого acknowledge не показывается как ошибка уже полученного
успешного действия; при несохранённом acknowledge pending остаётся доступен.
После подтверждённого получения результата следующее действие с новым ID —
новое намерение; система не запрещает осознанно создать ещё одну такую роль/смену.
Удаление userData/потеря журнала целиком не входит в гарантию process restart.

В Team Administration и Team Schedule добавлен общий Pending actions блок:
Recover -> явный повтор того же намерения с current authority;
Cancel pending action -> серверное ABANDONED или ответ alreadyCommitted.
Ссылка приглашения может быть показана при recovery; unavailable URL корректно
отображается, кнопка копирования пустой ссылки выключена. Account/auth event
сбрасывает видимые pending/link и отсекает поздние ответы recovery.
Если основной read временно недоступен, recovery остаётся на error surface;
оно не запускает reload, который уничтожил бы только что восстановленную ссылку.
Никакого скрытого auto-outbox/resend на startup не добавлено.
