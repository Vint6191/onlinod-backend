PROBLEM / ARCHITECTURE OF THIS CUTOVER
Earnings and Creator Analytics each had a global READY-catalog traversal and a
separate cycle lease. Failed creators could be passed by a global cursor; directory
admission could enumerate the entire busy due set. Those traversals also delayed
other recurring work. Existing CREATOR_RECURRING_PLANNING already had durable
per-creator identity, lifecycle publication/backfill, fair agency/shard claims,
restart/retry and a bounded timer pump. Reusing it avoids a second queue generation.

IMPLEMENTED TOGETHER
1. The existing bounded creator work consumer now invokes recurring Earnings and
   Creator Analytics for its exact claimed creator. Failures join its degraded
   result and existing durable retry/backoff; successful cycles retain durable
   next availability. No global cursor can silently skip a failed Analytics creator.
2. runAnalyticsCollectionSweep and runCreatorAnalyticsCatchupSweep are compatibility
   delegates into that same lane. Their global loops are removed. The hourly
   scheduler invokes the shared lane once, not three independent planners.
3. Analytics planning uses one root transaction per creator, bounded to 20 seconds:
   Agency SHARE -> Creator SHARE -> exact DomainWork claim -> collector/job planning.
   Eligibility is protected against soft deletion/status changes until commit.
   Exact work class, agency and creator identity must match the durable claim.
4. Claim authority is checked before planning and again after planning. Expiry,
   lost ownership or a superseding revision aborts the transaction. Jobs and any
   Campaign admission reservation roll back together. The shared commit helper now
   samples DB time AFTER taking the work-row lock, fixing stale pre-wait time.
5. Job publication has an async-scoped afterPlanningCommit boundary: job events
   are deduplicated and emitted after the transaction resolves; rollback discards
   them. Existing non-transactional callers retain their prior publication behavior.
6. Periodic Campaign directory admission uses a new fixed-size budget table. One
   production row owns UTC-hour reserved provider pages and job count across all
   replicas: atomic INSERT/ON CONFLICT, <=100 jobs/hour, guaranteed category credits.
   The first oversized request may proceed so size cannot make it impossible to
   serve. Later requests defer; canonical demand is preserved. This is admission,
   not a second OnlyFans start limiter. Initial/manual/provider-start paths keep
   their existing authorities. No capacity sharding or higher OF rate is invented.
7. Reservation occurs under the existing collector lock after active-job and
   current-state reads. Reused/busy jobs do not consume another reservation.
   The reservation shares the outer transaction with the planned job.
8. The former global discovery helper now requires <=100 explicit creator IDs,
   performs one candidate query, and rejects an unbounded call before SQL.
   It is no longer called by the recurring production path.
9. Capacity reporting remains on a separate hourly maintenance lane. Its global
   aggregate is explicitly NOT scale-closed yet, but it no longer precedes or
   authorizes the per-creator planning path. Until incremental capacity is proven,
   periodic admission uses conservative guaranteed credits even if a snapshot is
   HEALTHY. This can reduce directory admission versus the old normal 2400-call
   allowance. Existing canonical jobs/debt are not removed.
10. Existing creator lifecycle trigger, queue generation, indexes, topology and
    bootstrap remain the source of due work. This change needs no new catalog
    backfill and introduces no parallel per-creator queue.
