delete cascades DomainWorkItem and locator rows in its transaction; DWI deletion
queues deferred intents that remain until commit. The deferred flush then tried

partition, shard and Agency reconciliation, and affected real Agency deletion,
not only test fixtures. Suppressing the FK or changing teardown would hide it.

All three canonical functions now obey the same lifecycle protocol:
1. Lock an existing exact locator row before reading/reconciling child truth.
2. If absent, use an indexed EXISTS/LIMIT 1 child witness for that exact scope.
   If both locator and child are absent, return converged without inserting.
3. If a child exists, materialize through ON CONFLICT DO NOTHING covering both
   primary id and natural unique constraints. A successful INSERT already owns
   its row; use that ownership directly without a redundant second index lookup.
4. If another transaction won, retry the exact row lock, at most eight times.
5. Re-read child truth after owning the row, then finalize its head or delete it.
   The pre-insert witness is admission only, never the final due-time authority.

last prior child is deleted, that publisher waits, then creates/repairs the
locator from fresh child truth. An absence result cannot consume its publication.
