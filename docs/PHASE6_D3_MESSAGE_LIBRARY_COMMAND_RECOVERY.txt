2. BACKEND: СЕМЬ КОМАНД И ОДИН АТОМАРНЫЙ COMMIT

Новый владелец: src/services/message-library-command-service.js.
POST /api/server/content/message-library/commands/v3
POST /api/server/content/message-library/commands/v3/cancel
Actions: save, duplicate, trash, restore, permanent, block.trash, block.restore.
Envelope: UUID commandId, action, stable targetId, payload с creatorId.
UUID нормализуется в lower-case. Fingerprint включает версию 3, action,
targetId и полный канонический payload. Тот же ID с другим payload = conflict.
Ключ квитанции разделён по agencyId, userId и commandId.

Порядок: действующий actor/agency/creator/permission/billing -> receipt lock ->
поиск квитанции -> доменная операция -> обязательный AuditLog -> квитанция ->
один корневой commit. Вложенные существующие доменные транзакции присоединяются
к переданному tx; отдельный connection из единственного слота не требуется.
Профиль COMMAND / ReadCommitted / maxAttempts=1: существующие callbacks не
подписаны на неявный автоматический replay корня. Явный retry использует UUID.

Повтор проверяет актуальные права и billing ПЕРЕД чтением результата.
Cancel сохраняет ABANDONED-тумбстоун, либо сообщает alreadyCommitted.
Cancel не откатывает совершённое действие. После тумбстоуна поздний execute
того же намерения не выполняет действие. Для cancel нужна текущая membership;
потеря membership/аккаунта не даёт читать чужой журнал или чужую квитанцию.
Отмена валидирует UUID/envelope, но не требует корректности уже отклонённых
бизнес-полей: некорректная команда не должна навсегда занимать pending slot.
Тот же UUID после отмены нельзя присвоить исправленному payload.
Смена principal сохраняет незавершённую запись отдельно, не присваивает её
новому аккаунту. Отдельный административный recovery для удалённой membership
этим проходом не добавлялся.

Save сохраняет прежнюю защиту expected revision/server identity. Replay
распознаётся раньше повторной доменной проверки устаревшей версии.
Duplicate читает исходник под серверными блокировками, ограничивает active
blocks 500 и создаёт copy_<commandId> с детерминированными client IDs блоков.
Пара source/target namespace блокируется в одном сортированном порядке.
Нет Desktop-поиска по 100 страницам для операции duplicate.
Все media проверяются существующим provenance classifier внутри того же tx;
обхода GENERAL/CUSTOM при копировании нет. Проверка обходит ВСЕ чанки по 200,
в пределах существующего лимита 2000 различных media IDs на script.

Семь старых unkeyed HTTP management writes возвращают 410 с кодом
MESSAGE_LIBRARY_COMMAND_V3_REQUIRED. Старый Desktop не сможет ими писать.
При будущем внедрении Backend/Desktop требуют согласованного обновления;
сейчас пакет устанавливать не предписано.

3. КВИТАНЦИИ НЕ ПРЕВРАЩЕНЫ В СКРЫТЫЙ АРХИВ СОДЕРЖИМОГО

Новая таблица MessageLibraryCommandReceipt содержит компактную ссылку на
совершённый результат и его digest, а не копию title/text/media.
Первый ответ содержит сам результат. Повтор читает только тот же server ID
в том же agency/creator, берёт namespace/row lock и сверяет digest.
Если результат изменён, очищен или client ID использован новым объектом,
ответ подтверждает совершённую команду, возвращая resultUnavailable=true и
item/block=null. Старое содержимое не перезаписывается и не воскрешается.
Renderer после recovery обновляет канонический список.
Содержимое удалённого скрипта не остаётся в этой новой серверной таблице.
Это не утверждение о стирании внешних бэкапов или всех старых таблиц продукта.

Новая миграция:
prisma/migrations/20260929190000_phase6_message_library_command_receipts/migration.sql
PK по id, индекс (agencyId,id), CHECK статуса, CHECK размера result <=4 MiB.
Квитанции переживают удаление скрипта и не удаляются по короткому TTL: иначе
поздний повтор мог бы снова выполнить операцию. Очистка Agency включает таблицу
в существующий ограниченный non-FK purge с индексированным id-отбором.
SQL-проверка purge с limit=2 оставляет квитанции другой agency нетронутыми.
Все ранее выпущенные миграции неизменны; новая схема проверена Prisma validate.

4. DESKTOP: СОХРАНЯЕМОЕ НАМЕРЕНИЕ ДО HTTP И RECOVERY В ИНТЕРФЕЙСЕ

Из D2 выделен DurableCommandTransport с конфигурацией домена. Team сохраняет
совместимый фасад TeamCommandTransport, прежний endpoint, proof и journal path.
Message Library использует message-library-command-pending-v1.json и свой
endpoint v3. Журнал: максимум 32 записи / 4 MiB; payload ML <=2 MiB.
UUID и payload записываются атомарно до отправки HTTP. Ошибка записи не
позволяет отправить запрос. Повреждённый журнал не сбрасывается молча.
Ключ pending: backend/user/agency + creator/script. Незавершённое действие
блокирует другое намерение для того же script; разные creators разделены.

После HTTP reply запись помечается received, но не забывается до Renderer ACK.
Потерянный IPC-ответ/перезапуск не порождает новый commandId. Потерянный ответ
самого ACK не превращает известный успех в предложение повторить действие.
Отмена сначала получает серверное подтверждение/тумбстоун, затем забывает запись.
Проверка incarnation после proof/HTTP не публикует ответ в изменённый аккаунт.
Media URL допустимы в payload, authentication/token/password поля отвергаются
перед сохранением. Журнал намеренно содержит пользовательский черновик для
recovery; это не серверный архив и не кеш всех завершённых scripts.

Все пять Main management entrypoints используют общий transport. Duplicate
больше не выполняет list-search и не генерирует новые IDs в Main.
Renderer adapter подтверждает команды в своём RPC-домене. Общая панель
незавершённых действий подключена к Message Library, предлагает Recover/Cancel
и после подтверждения вызывает штатный refresh текущего creator. Этот refresh
обновляет список и сохраняет существующий отдельный draft; generation-защита
панели сбрасывается на смене authorization context.
Фоновая maintenance/purge остаётся своей операцией, не новой пользовательской
командой. D1 usage path и sidecar attribution сохранены.
