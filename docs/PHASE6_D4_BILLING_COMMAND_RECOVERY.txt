3. BACKEND: ВЛАДЕЛЕЦ ОСТАЁТСЯ BILLINGORDER

Новый маршрут POST /api/billing/wallet/top-up/v2 принимает:
commandId UUID, action=wallet.topup, targetId="",
payload={amountCents: целое 100..10000000, testMode: boolean}.
Envelope и payload строгие. Agency/user берутся из auth, не из Renderer.
UUID нормализуется в lower-case. Сумма связана с существующим requestHash.
Существующий заказ также связан с createdByUserId; другой actor не присваивает
его UUID. Sandbox/live не могут незаметно сменить смысл того же намерения.
Серверный mutex на agency/UUID и проверка противоположного testMode защищают
идентичность при смене окружения. Повтор старого окружения может вернуть
метаданные своего заказа, но не чужой по окружению платёжный URL.

Порядок создания:
- Короткий commit: текущие agency/user/member/epoch, OWNER, поиск резервации,
  проверки суммы/окружения/FREE_INTERNAL, создание BillingOrder CREATED.
- После commit создатель резервации делает единственный provider POST.
- Короткое сохранение метаданных. Статус CHECKOUT_CREATED присваивается только
  через CAS по CREATED. Более поздние PROCESSING/PARTIALLY_PAID/PAID/REFUNDED/
  EXPIRED/FAILED/CANCELLED не откатываются.
- Перед выдачей результата/URL заново проверяются текущие права и accessEpoch.

Один BillingOrder остаётся канонической резервацией; отдельная таблица HTTP-
квитанций для денег не введена. P2002 читается после выхода из неудачной
транзакции, на новом корне. Внешний HTTP не находится внутри DB retry callback.
Ни HTTP replay, ни старый FAILED sandbox-заказ не запускают второй invoice POST.
После таймаута/повреждённого ответа условная запись сохраняет
providerStatus=INVOICE_OUTCOME_UNKNOWN лишь для ещё CREATED заказа без invoice.
Это не отменяет и не затирает опережающий IPN.

Ответ содержит commandId, canonical order, checkoutUrl, recoveryNote,
recoveryPending. Терминальный заказ не открывается как новый checkout.
Неизвестный или недоступный в текущем окружении незавершённый счёт остаётся
recoveryPending=true. Повтор читает существующую резервацию.

POST /wallet/top-up без v2 возвращает 410 BILLING_COMMAND_CLIENT_UPGRADE_REQUIRED.
При будущем внедрении Backend/Desktop требуют согласованного обновления.
POST /orders/:orderId/resume использует текущую live authority владельца.
Старые /quote и /checkout остаются 410. Неиспользуемый legacy createCheckout
не объявляется новым проверенным платёжным маршрутом.

Обработка HMAC IPN, монотонный payment status, idempotency keys topup:<orderId>
и topup-refund:<orderId>, раздельные sandbox/live wallets сохранены.
Audit создания счёта остаётся существующим best effort. Его ошибка не является
доказательством отсутствия платежа. Требование обязательного transactional
AuditLog из Team/Message Library не перенесено механически на внешний invoice.
Другие Billing-команды (preferences/start/cancel-renewal/reconcile) не объявлены
полностью повторно проверенными этим D4.

4. DESKTOP И ЧЕСТНОЕ ВОССТАНОВЛЕНИЕ НЕИЗВЕСТНОГО ИСХОДА

Settings использует общий DurableCommandTransport и отдельный файл
billing-checkout-pending-v1.json. До HTTP атомарно записываются UUID, amount,
testMode и namespace principal (backend/user/agency). Один unresolved slot
wallet.topup на principal. Журнал сохраняется при shutdown/logout/account switch.
Новый principal не читает и не подтверждает записи предыдущего аккаунта.
Общие лимиты 32 записи/4 MiB сохранены; payload Billing ограничен 1 KiB.
Токены, платёжные URL, provider secrets в журнал не записываются.

В Plan & Billing есть панель незавершённых действий с Recover.
RPC: billingCheckoutCommands.listPending / retry / acknowledge.
Автоматического provider resend при монтировании UI или старте Desktop нет.
Cancel для Billing отсутствует в RPC/UI и запрещён самим transport config:
неизвестный внешний результат нельзя объявить отменённым локальным действием.

ACK разрешён только при recoveryPending=false. Неизвестный исход не удаляется
из журнала даже после успешной доставки HTTP/IPC-ответа: повторный Top up той же
суммы сохраняет UUID, новая сумма или окружение блокируются до разрешения
старого действия. Renderer также не отправляет ACK для recoveryPending=true.
После подтверждённого результата потеря ACK-ответа не превращается в ошибку,
которая приглашала бы создать ещё один платёж.

Перед открытием checkout и после асинхронного результата проверяется permit.
Смена principal закрывает платёжное окно; поздний ответ не открывается в новой
сессии. Resume тоже проверяет permit после HTTP. Ошибка открытия окна возвращает
уже известный order с подсказкой открыть его из Payment history.

Существенное ограничение: локальная резервация не способна восстановить
потерянный invoice URL, если провайдер не вернул ни ответ, ни проверяемое
уведомление. Такой случай остаётся unresolved до подтверждения исхода по
существующему заказу/провайдеру. Новый автоматический счёт и фиктивная отмена
не используются для обхода этой неопределённости. Самостоятельный операторский
workflow доказанного NO_EFFECT этим проходом не добавлялся.

5. TEAM: ОТМЕНА ОШИБОЧНОГО НАМЕРЕНИЯ

parseCommand(input,{cancel}) всегда валидирует UUID/envelope и предел payload
1 MiB. Валидный бизнес-payload нормализуется прежней схемой v2; его fingerprint
не меняется. Для cancel ошибочный payload допускается как bounded raw intent.
Текущая membership всё равно проверяется под серверной authority. Cancel
сохраняет ABANDONED, повтор cancel возвращает ту же развязку. Исправленный payload
с тем же UUID получает TEAM_COMMAND_INTENT_MISMATCH. Отмена после commit не
откатывает выполненную операцию. SQL-проверка использует реальный receipt.

- Disable sole owner нарушал уже существующий generation/single-owner gate.

  что disabledAt действительно сохранён. Триггеры не отключались.
- Понижение OWNER увеличивает accessEpoch. Проверены оба ответа: stale admitted
  membership отклоняется; свежий ADMIN также не получает owner-authority.

Следующий связанный объём 6D:
1) Управляющие записи Settings/creator/network и secret/session/keyring recovery.
   У generic pool proxy create нет command ID; Desktop использует другой,
   creator-bound CAS маршрут. Нужно проверить допустимость первого маршрута,

   имеющийся clientMutationId доказательством закрытия остальных subcommands.
3) Довести job/progress, programmatic writes/settlement, observations/refresh,
   module controls по их существующим revision/token/generation контрактам.
   Сохранить право узкого settlement после commit и запрет UNKNOWN resend.

6F (сквозная приёмка, полноценный build, реальный Electron/несколько ПК,
