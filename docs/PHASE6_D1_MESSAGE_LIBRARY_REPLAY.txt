2. КОНКРЕТНЫЙ ЭФФЕКТ D1

До D1 POST /api/server/content/message-library/usage каждый раз выполнял
contentUsageEvent.create с новым серверным id внутри действующего lifecycle
commit. Актуальная авторизация, script lock и audit уже существовали, но они
не связывали два HTTP запроса с одним пользовательским действием.
Потеря ответа после commit и повтор того же события создавали второй факт.
Это исходный P6-F7, а не регрессия A2 или новой миграции.

Новый контракт:
- POST /api/server/content/message-library/usage/v2.
- Обязательный eventId: строка 16..120 символов, [A-Za-z0-9:_-], первый символ
  буквенно-цифровой. ID не обрезается и не генерируется на сервере/Main.
- Один intent = один стабильный ID на всех повторах. Новое реальное действие
  получает новый ID, даже если шаблон и dialog прежние.
- Первая запись: HTTP 201, replayed:false, event.
- Успешный повтор: HTTP 200, replayed:true, тот же event/id/createdAt.
- Тот же ID с другими сохраняемыми данными: HTTP 409,
  MESSAGE_LIBRARY_USAGE_EVENT_CONFLICT, без новой записи/аудита.
- Отсутствующий/невалидный ID: 400 MESSAGE_LIBRARY_USAGE_EVENT_ID_REQUIRED.
- Не конечные числовые суммы: 400 MESSAGE_LIBRARY_USAGE_NUMBER_INVALID.
- Старый POST /message-library/usage возвращает 410
  MESSAGE_LIBRARY_USAGE_CLIENT_UPDATE_REQUIRED. GET /usage сохранён.

2.1 КВИТАНЦИЯ — САМО КАНОНИЧЕСКОЕ СОБЫТИЕ

Новый message-library-usage-service.js формирует id:
ml_usage_v2_ + SHA256(JSON([agencyId, userId, eventId])).
Identity ограничена агентством и пользователем, но намеренно не script/creator:
повтор ключа с другой целью конфликтует, если текущий доступ к ней допускает
сам запрос. Другой агентство/пользователь — другое пространство ключей.
Криптографический hash здесь идентичность, не credential или право доступа.

Fingerprint версии 2 строится по фиксированному нормализованному представлению
сохраняемых полей: creator, fan, dialog, тип события, source, script/message,
draft/provider-message ids, amount/currency, mediaCount/price/lockedText.
Сервер добавляет metadata.usageReceipt={version:2,eventId,fingerprint}.
Клиент не может передать собственную квитанцию через metadata: разрешённый
список её отбрасывает. Сырые chat text/rawEvent не сохраняются и не хешируются.
Порядок произвольных ключей metadata на fingerprint не влияет.

ContentUsageEvent уже имеет primary key. Новых таблиц/колонок/индексов/миграции
в D1 не требуется; старая история не сканируется и не переписывается.
Это сохраняемый доменный результат, а не Map/HTTP-cache с TTL.

Последовательность одного commit:
1) Agency lifecycle/billing read barrier, live Creator, User, current Member,
   epoch и creator scope; в product HTTP context — текущие billing facts.
2) Transaction-scoped advisory lock по event identity.
3) Point lookup ContentUsageEvent по primary key.
4) Если квитанция есть: сверить agency/user/creator, версию, ID и fingerprint;
   вернуть исходный факт. Второй audit не добавлять.
5) Если её нет: взять существующий script lock, проверить creator/kind,
   существование и trash-статус script и выбранного block.
   Читается только выбранный block, список всех blocks для usage не загружается.
6) Взять время БД, создать событие и audit в том же transaction; вернуть 201.

Ошибка audit откатывает и событие; повтор может записаться после устранения
ошибки. Ошибка до commit не резервирует ключ навсегда. Потеря ответа после
commit позволяет прочитать уже сохранённую квитанцию после перезапуска сервера.
Основной unique PK остаётся последним ограничителем дублирования. Advisory lock
позволяет штатному конкурентному повтору дождаться исхода и прочитать квитанцию.
ReadCommitted callback использует общий commit kernel; скрытых внутренних
повторов внешних эффектов или отдельного владельца transaction нет.

Свежая авторизация проверяется ДО чтения квитанции. Повтор не возвращает
сохранённый результат после отзыва membership/creator scope, смены epoch,
отключения пользователя, retirement creator/agency либо billing hold.
Этот контракт относится к новым usage-командам; его нельзя механически
распространять на settlement уже совершённых OF/Telegram отправок, где другая
политика сохранения внешнего факта после потери текущих пользовательских прав.

Удаление/trash script или block после успешного события не уничтожает квитанцию:
существующий факт можно повторно подтвердить при сохранённых текущих правах на
creator. Новый intent к уже удалённому script отклоняется. ContentUsageEvent
не имеет каскадной связи с script/block, что проверено по текущей схеме.

СРОК ГАРАНТИИ: пока сохранён канонический ContentUsageEvent. В D1 нет TTL/GC
квитанций и нет удаления старой истории. Полный destructive purge может удалить
эти факты; доступ к retired/purged creator сейчас закрывает lifecycle authority.
Будущий Phase7 purge событий живого creator обязан определить retention/tombstone
и срок повтора, прежде чем удалять квитанции. После произвольного удаления event
вечная дедупликация не обещается. Старые дубликаты не объединены задним числом.

2.2 DESKTOP INTENT И СОХРАНЁННЫЕ ГРАНИЦЫ

Shared MessageLibraryRecordUsageInput теперь требует eventId; UsageResult
содержит replayed. Sidecar создаёт crypto.randomUUID один раз перед ожиданием
applyMessageDraft. Только complete evidence запускает usage; тип остаётся
'draft_inserted' — подтверждение фактической OF отправки этим не подменяется.

Снимок creator/tab/webContents/dialog сравнивается после ожидания bridge.
Поздний ответ после навигации не переносит статус/usage в другой диалог.
Защита destroy/applyGeneration сохранена. Main по-прежнему связывает Sidecar
с реальными текущими creator/dialog и не принимает подмену scope из renderer.
Main проверяет переданный eventId и пересылает его неизменным на /usage/v2;
обновление токена в BackendApiClient повторяет тот же body.

Desktop НЕ получил durable outbox или новый автоматический retry. Использование
шаблона по-прежнему доступно при недоступной telemetry, и offline event может
не попасть на сервер. Дедупликация уже доставляемого intent не равна гарантии
доставки каждого события. После закрытия Desktop незавершённый intent здесь не
восстанавливается. Новая вставка после перезапуска — новое действие с новым ID.
