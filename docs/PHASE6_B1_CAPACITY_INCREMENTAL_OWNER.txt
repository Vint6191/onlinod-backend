3. ВЛАДЕЛЕЦ И ПРОТОКОЛ
Новый provider-capacity-projection-service.js выполняет одну bounded transaction
через существующий db-commit-kernel/runDbTransaction. Внутри:
1) pg_try_advisory_xact_lock('phase6-capacity-projection-v1') и lock singleton
   progress state. Занятый owner возвращает capacity_projection_busy до чтения
   canonical relations; это cold projection lock, canonical writers его не берут.
2) Проверка поколения и полного current job catalog. Изменённый каталог требует
   отдельного перехода/повторного backfill; нельзя молча забыть старые JobInstance.
3) DB authority time, ограниченные keyset страницы первичного обхода трёх таблиц.
4) Индексированный wakeup nextDueAt и bounded dirty repair.
5) Обновление contributions и aggregate deltas; удаление обработанных dirty keys.
6) Новое DB время, revision, согласованный input read, derivation и публикация.
Всё коммитится или откатывается вместе. Между вычислением и записью нет свободно
живущего lease callback. По завершении/разрыве транзакции PostgreSQL освобождает
owner lock. Старый вычислитель не может продолжить публикацию в новом owner.

root timeout=15000ms, maxWait=2000ms, общий deadline=20000ms,
lock_timeout=2000ms, statement_timeout<=12000ms; максимум 3 попытки только для
известного rollback conflict/deadlock через существующий kernel. Неизвестный
исход commit не повторяется автоматически. Bounded work содержит только DB facts,
нет внешнего HTTP/OF/AI или недолговечных обязательных side effects.

4. ИНКРЕМЕНТАЛЬНОЕ СОСТОЯНИЕ
Новая additive migration20260929150000_phase6_capacity_incremental_v1:
- ProviderCapacityProjectionState: generation, catalog, revision, три durable
  keyset cursor/completion flags, sampledAt. Один существующий OF topology ID.
- ProviderCapacityDirty: один ключ (kind,sourceId), FIFO по первоначальному
  touchedAt. Повторное изменение горячего source не отправляет его в конец.
- ProviderCapacityContribution: typed current вклад конкретного canonical row,
  bucket, counts/calls, oldestAt и nextDueAt. Нет foreign key к source: удаление
  должно успеть вычесть прежний вклад после исчезновения canonical row.
- ProviderCapacityBucket: точные BigInt sums по directory, fan и конечному каталогу
  job classes. Перед отрицательной delta создаётся нулевой bucket отдельно:
  отрицательная INSERT строка не проходит PostgreSQL CHECK даже при ON CONFLICT.
- Два поля результата: projectionRevision и projectionCoverageStatus.

AFTER INSERT/DELETE/UPDATE OF релевантные поля на CreatorCampaignCollectionState,
CreatorFanRefreshDemand и JobInstance сохраняют dirty в canonical transaction.
Откат canonical mutation откатывает сигнал. Старые версии Backend тоже проходят
через DB triggers; обход через прежний ORM или raw SQL не теряет изменение.
Редкий rewrite id ставит dirty для старого и нового ключа. TRUNCATE не является
поддерживаемым live mutation protocol; активных TRUNCATE этих таблиц в source
call graph не найдено. Будущий purge/rebuild требует собственного согласования.

Размер repair default96, runtime clamp3..128. На source kind backfill page =
max(1,floor(batch/3)); суммарно не более batch source IDs за проход. Time wakeup
не более batch и dirty claims не более batch. Ни cursor, ни dirty rows не живут
только в RAM. Пустая завершающая страница корректно завершает точный кратный batch.
Изменение/вставка позади cursor остаётся в trigger queue и не теряется.

Repair берёт dirty rows FOR UPDATE SKIP LOCKED, читает canonical по PK IN/ANY
ограниченного массива, читает прежние вклады, вычисляет разность и публикует её.
Concurrent canonical writer может ждать конкретный dirty key. После commit repair
его trigger снова создаёт key: pending изменение не стирается удалением очереди.
Изменения нескольких ключей могут вызвать обычный deadlock — bounded timeout и
rollback retry обязательны; реальное двухклиентное ожидание ещё требует gate.

Time semantics прежние: due <= sampled time; overdue строго <. В точном равенстве
ставится следующий wakeup на +1ms. При прошедшем deadline nextDueAt удаляется,
поэтому уже overdue запись не перезапускает сама себя вечно. Новое изменение
deadline снова пересчитывается через trigger. Во время final read любые ещё
неотработанные deadlines сохраняют PARTIAL.

Oldest dates читаются indexed ORDER BY/LIMIT1. Background class counts и суммы
перебирают только фиксированный каталог job buckets; per-class minimum берётся
через lateral indexed LIMIT1. Нет агрегирования всей истории/очереди в refresh.
Таблицы current contributions/dirty растут с числом актуальных source facts;
ограничен один проход и оперативный объём, не выдуман глобальный лимит canonical
истории. Физическая пропускная способность и уборка MVCC/bloat не измерялись.

5. CORRECTNESS И COVERAGE
Partial bootstrap, непустая dirty queue или overdue wakeup => projection PARTIAL,
future debt coverage PARTIAL, status UNKNOWN, admission CONSERVATIVE. Нулевой
текущий partial sum не превращается в HEALTHY. COMPLETE_AT_SAMPLE означает
состояние в момент наблюдения, а не обещание отсутствия будущих изменений.
Даже при complete projection background_other pending jobs по-прежнему дают
UNKNOWN, пока неизвестна точная будущая cardinality OF calls. Сохранён A18 contract:
не подменять неизвестные calls числом Jobs. Actual usage accounting и topology
v1, один of-global gate, 700ms физическая authority, weighted provider credits и
conservative admission semantics не заменялись и не масштабировались шардированием.

publication trigger проверяет новую sourceVersion, transaction-local marker,
актуальную projection revision/generation. Повтор/регресс revision и sampledAt
отклоняются. JS persist также требует kernel-issued transaction context и не
возвращает success при пустом RETURNING. Marker выставляется только после
incremental repair и input read. Старые binaries с прежней sourceVersion получают
подавленную запись (RETURN NULL), поэтому не могут затереть новую authority.
Миграция сразу переводит прежний singleton в UNKNOWN/CONSERVATIVE.
Старый full scan может продолжаться на ещё не обновлённой реплике, но не публикует;
после завершения rollout этот code path из автоматических вызовов исчезает.

Migration обёрнута BEGIN/COMMIT с lock_timeout5s. Таблицы/индексы новые и пустые,
нет bootstrap INSERT SELECT всей истории в DDL, нет DROP/TRUNCATE canonical data,
старые migration bytes не изменены. DDL lock и roll-forward поведение надо проверить
на обычном PostgreSQL. При откате только бинарника следует сохранить additive
схему и ожидать conservative stale reporting; отключать guard ради старой записи
не входит в этот пакет. Не выполнялись upgrade/downgrade production DB.
