2. ПОДТВЕРЖДЁННЫЙ ПРОБЕЛ D5

Серверные CAS/проверки прав не восстанавливали результат потерянного HTTP/IPC.
Desktop отправлял профиль, workspace, создание creator и сетевые изменения
на старые маршруты без сохранённого до отправки ID команды. После commit и
потери ответа повтор мог получить duplicate/CAS conflict; после перезапуска
не было надёжного способа подтвердить именно это действие. У зашифрованного
proxy REPLACE повторная подготовка также создаёт другой случайный ciphertext.

Дополнительно у профиля не было условия «имя, которое пользователь редактировал,
всё ещё актуально». Два исполняемых сценария воспроизводят перезапись старым
редактором на D5 (включая expectedName=null) и проходят на D6.
Workspace теперь проверяет отпечаток именно редактируемого снимка настроек.
Это сравнение значений, а не обещание нового глобального monotonic version.

3. СЕРВЕРНЫЙ КОНТРАКТ

Новый /api/management/commands/v1 и /v1/cancel, оба с authRequired.
Восемь строго заданных действий:
- account.profile: новое имя + expectedName.
- workspace.update: patch + expectedRevision снимка name/preferences.
- creator.create: displayName, username, notes; проверка broad creator scope.
- creator.update: ограниченные метаданные + expectedUpdatedAt; запрет ручной
  подмены username подключённой модели сохранён.
- network.create: creator-bound proxy + expectedNetworkVersion + deviceId.
- network.update: endpoint + expectedVersion + deviceId, KEEP/REPLACE/CLEAR.
- network.delete: endpoint + expectedVersion.
- network.assign: creator + expectedVersion + DIRECT/PROXY и endpoint.

Fingerprint связывает action, target и точный payload, сохраняя различие intent.
Ключ квитанции включает agencyId/userId/UUID. Отдельный ID нельзя использовать
для другого тела, действия или цели. JSON строгий, payload не больше 1 100 KiB.
Обычный endpoint не принимает plaintext password; REPLACE принимает только
CLIENT_E2E_V1 envelope. Device-bound token должен совпадать с сохранённым deviceId.

Корневой DB commit: Agency lifecycle barrier, mutex команды, чтение прежней
квитанции, текущие creator scope/User/Member/permissions/accessEpoch, доменная
операция, required audit и квитанция. Все части используют одну транзакцию.
Network и enrollment теперь явно присоединяются к kernel-issued transaction
с Serializable isolation; отдельный вложенный root по-прежнему запрещён.
Автоматические повторы произвольных callbacks не включены: одна DB попытка,
явный повтор клиента использует тот же сохранённый ID.

Account setter сохраняет User advisory/row lock order. Workspace сериализует
проверку snapshot digest и запись через workspace advisory lock. Network
сохраняет прежние версии, dedicated ownership, E2E checks и запрет отключения/
удаления назначенного proxy. Existing domain owners остаются владельцами этих
правил; новая квитанция не заменяет их общим кешем HTTP-ответов.

COMMITTED receipt хранит fingerprint и небольшой locator/digest результата,
не исходное тело, пароль, ciphertext, заметки или копию профиля. На replay:
- снова проверяются живые права и scope, включая исходный scope удалённого proxy;
- по locator читается текущее каноническое состояние;
- прежнее состояние не записывается повторно;
- если состояние изменилось, возвращается подтверждение commit с
  resultUnavailable=true и result=null. UI предлагает проверить текущие данные.
Удаление proxy не выполняется второй раз даже после повторного использования ID.

Канонический ответ ограничен 256 KiB, квитанция — 8 KiB. Слишком большой новый
результат откатывает mutation; слишком большой/изменённый replay недоступен как
снимок и не переписывает канонические данные. Network hint откладывается до commit.
Отмена проверяет текущего участника, сохраняет ABANDONED tombstone даже для
некорректного бизнес-payload и сериализуется с выполнением. Если действие уже
завершено, возвращает alreadyCommitted без отмены его эффекта. Если действие
ещё не выполнено, поздний исходный запрос больше не сможет его выполнить.
Отмена не требует прежнего creator permission и не возвращает содержимое
результата: участник с изменёнными правами может убрать собственный pending intent.
Disabled/retired actor не получает эту возможность через старую сессию.

Квитанции не очищаются по произвольному TTL, иначе старый запрос мог бы стать
новым. Они включены в существующую ограниченную очистку при удалении Agency,
с индексом (agencyId,id). Один OWNER не менялся и проверен SQL-fixture lifecycle.

4. DESKTOP И UI

Новый ManagementCommandTransport использует проверенный AtomicJsonStore и
DurableCommandTransport. Журнал management-command-pending-v1.json сохраняется
с fsync до POST. UUID и payload переживают потерю ответа, IPC и Main restart.
Windows backup-only window восстанавливается; повреждение/ошибка диска не
обнуляет intent и не приводит к отправке новой случайной команды.

Сохранены лимиты общей инфраструктуры: 32 pending entry и 4 MiB всего журнала;
account/backend/agency principal и login incarnation отделяют чужие результаты.
Один unresolved resource slot не допускает другой intent. Одновременный
одинаковый клик объединяется. Перед отправкой и после ответа проверяется текущий
локальный permit; это дополняет, но не заменяет серверную проверку.

Проверяются не только ok/commandId: action, флаги replay, наличие целевого
user/creator/proxy/profile, ID и версии. Некорректный ответ не разрешает ACK.
Команда остаётся до подтверждения получения Renderer. Потеря ответа на ACK
не превращает уже полученный успех в ошибку, предлагающую повторное создание.
Cancel удаляет запись только после подтверждённого terminal server result.

Семь существующих Main/UI путей переведены: create creator, profile, workspace,
create/update/delete proxy, assign network. Существующего Desktop-редактора
общих creator metadata в источниках не найдено; серверная creator.update
реализована и SQL-проверена, новый экран/кнопка метаданных не выдумывались.

Панель Recover/Cancel доступна в Settings независимо от загрузки его остальных
данных, в Creator Management и в Creator Overview. В списке моделей панель не
дублируется в каждой строке. Восстановление обновляет нужные queries/network
view; подтверждённая отмена тоже сбрасывает creator bootstrap cache. getState
обновляет локальную проекцию user после проверки текущего presentation permit.

Proxy credentials шифруются существующим keyring до journal/HTTP. В обычный
журнал попадает уже CLIENT_E2E_V1 ciphertext и маскированный username hint.
Recovery переиспользует именно этот ciphertext и не требует повторно вводить
или сохранять plaintext password. Тест исполняет реальный Main network service
с управляемым encryptor и проверяет отсутствие исходных username/password
в файле. Это не native OS keychain proof и не новая криптосхема.
D5 root-recovery journal по-прежнему отдельный, OS-protected; AMK/recovery key
никогда не переносились в generic management journal.

Восемь старых unkeyed HTTP-записей имеют ранний 410 gateway до старых handlers:
POST /api/creators; PATCH /api/creators/:id;
PATCH /api/settings/account/profile; PATCH /api/settings/workspace;

PATCH и DELETE /api/network-profiles/proxies/:proxyId;

Gateway учитывает default case-insensitive routing Express и trailing slash.
Unowned POST /proxies уже был закрыт в D5. Старые тела handlers сохранены за
явным gateway на период cutover, а не считаются достижимыми mutation paths.

Backend + Desktop + migration являются согласованным исходным пакетом.
Старый Desktop для этих восьми маршрутов получит 410; новый Desktop со старым
сервером не делает тихий fallback на опасный unkeyed write. Это не инструкция
устанавливать сейчас: вердикт «СТАВИТЬ: ПОКА НЕТ» сохраняется до общих gates.

Password/avatar, root/device/creator rotations, Telegram challenges, creator
connection/lifecycle/observations и provider secret-read/test-material не
обёрнуты в этот протокол. Их текущие владельцы и replay/recovery правила
рассматриваются отдельно; здесь их полное закрытие не заявляется.
