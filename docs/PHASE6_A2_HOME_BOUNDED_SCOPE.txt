2. ЧТО ИМЕННО ИЗМЕНИЛОСЬ

2.1. Compact membership authority / relation-based scope

Новый home-scope-repository.js читает актуальные agency/member/user/accessEpoch,
role/roleKey/permissions и вычисляет broad в PostgreSQL. Полный assignedCreators
не возвращается в Node. Restricted scope использует существующую
AgencyMemberCreatorAccessCurrent, сверяя agencyId, memberId, accessEpoch,
creatorId и текущую живую CreatorAccount. Для restricted scope обязательно
ACTIVE-поколение phase3_domain_work_claim_topology_a36_v1. Отсутствующая/неполная
проекция даёт HOME_SCOPE_PROJECTION_NOT_READY 503; не превращается в пустой
список или незаметное перечисление JSON.

SQL отдельно проверяет живое агентство, активного участника и неотключённого
пользователя. Broad owner остаётся независимым от списка назначений.
Billing сохраняет текущую продуктовую семантику: support hold, FREE_INTERNAL,
trial, coreValidFrom/coreValidUntil по времени PostgreSQL. Предикат применяется
до page LIMIT и до итогового count. Страница не теряет оплаченные модели из-за
того, что неоплаченные заняли лимит раньше фильтрации.

Для /api/home подключён homeAuthRequired: те же проверки токена, device session,
logout, disabled user, email verification, но членство выбирается без полного
assignedCreators. Другие маршруты продолжают использовать прежний authRequired.
Это не глобальная переделка входа и не ослабление авторизации.

В начале и конце Home read проверяется актуальный membership epoch. Смена прав
в ходе чтения отменяет ответ целиком. Это не обещание вечной актуальности уже
отданного экрана; Desktop также отбрасывает ответы устаревшего local permit.
Чтения Home read-only. Они не создают JobInstance и не запускают AI/OF сами.

2.2. Summary and creator pages

GET /api/home/summary?range=<today|7d|30d|90d>&contractVersion=2
возвращает сводные значения. В Node не выгружаются все CreatorAccount,
AgencyMember или WorkerDevice. Участники/устройства считаются SQL COUNT,
очередь — SQL GROUP BY в текущем scope. audit по-прежнему максимум 5 записей.
Чувствительные разделы по-прежнему зависят от money.view_earnings,
workspace.view_team, workspace.view_audit, workspace.manage_settings;
billing/seats — только owner. В текущей Prisma-модели AgencySubscription нет
seatsLimit: не запрашиваем несуществующее поле; limit/remaining остаются unknown.

Summary имеет contractVersion=2. creatorScope содержит mode, accessEpoch,
totalCreators; creatorIds=[], creators=[], pending.creatorIds=[], pending.jobs=[].
Это осознанный новый договор: полные списки перестали быть частью сводки.
Старый клиент без contractVersion=2 получает 409 HOME_CLIENT_UPDATE_REQUIRED
с просьбой обновить Desktop, а не ложный «пустой полный список».

GET /api/home/creators?range=<key>&limit=50&after=<last-id>
возвращает ровно страницу и явные nextCursor/limit/order/refreshedAt/accessEpoch.
По умолчанию 50, разрешено 1..100, выборка с одним lookahead. Cursor — id,
максимум 180 символов, управляющие символы отклоняются. Порядок id_asc;
никакого OFFSET, no 5000/10000 correctness horizon. Фильтры agency/epoch,
permissions и billing проверяются заново для каждой страницы.
Это живой keyset-list, не зафиксированный архивный snapshot: вставка с id
перед курсором станет видна после возврата на первую страницу. Удаление модели
или курсора не блокирует продолжение. Сортировка по глобальному доходу не
обещается: прежняя полная сортировка заменена стабильной пагинацией по id.

2.3. Coverage-aware canonical revenue SQL

home-read-repository.js сводит канонические AnalyticsCoverage + COMMITTED
AnalyticsScanProof + CreatorEarningsDaily в PostgreSQL. Текущий/предыдущий
периоды различаются; максимальный Home диапазон 90 дней, вместе до 180.
Ответ summary содержит один aggregate и максимум 90 точек UTC-графика.
Ответ страницы содержит показатели только её моделей, не весь scope.

UNKNOWN != ZERO сохранено. Для reporting нужны И достаточное доказанное
покрытие, И все дневные строки с COMMITTED proof. Найденный дополнительный
разрыв старого алгоритма закрыт: COMPLETE coverage при пропавшей дневной строке
больше не даёт «полный» headline KPI и график. Индивидуально подтверждённые
модели остаются видимыми. Полный ноль для действительно пустого scope допустим;
неизвестный доход неполного непустого scope — null.

PARTIAL текущего дня с COMMITTED proof остаётся пригодным. Свежесть:
15 минут today, 48 часов recent closed, 30 дней historical; timestamp > now+5min
не считается свежим. Delta показывается только при полных и свежих текущем
и предыдущем периодах и ненулевом предыдущем итоге. Большие суммы проверяются
на Number.isSafeInteger; переполнение не округляется молча.

Pending считается SQL EXISTS: активная materialized job либо актуальный demand,
действительно включающий модель в scope запросившего участника. Нет прежнего
take:50 для demands. Null creatorIds означает текущий scope этого участника,
а не все модели агентства. Просроченный epoch/disabled/deactivated requester
не расширяет индикатор ожидания. Полный список pending IDs не передаётся.
Это индикатор наличия ожидающей работы, не обещание времени её завершения.

SQL объём результата/параметров ограничен. Агрегация по агентству всё равно
читает релевантные C×days канонические строки внутри PostgreSQL; её стоимость
не объявляется O(1). Общая нагрузка многих агентств и 100 workers не доказана
одним fixture. Audit metadata/строковые поля по-прежнему не имеют нового
общего byte-budget; измеренные 13.6KB — размер конкретных тестовых данных,
не универсальный жёсткий лимит HTTP-ответа.

2.4. Query-plan finding during implementation

На промежуточной версии явные константные предикаты agency/member заставили
PostgreSQL без ANALYZE недооценить размер нового membership. Nested loop
перечитывал агентство для каждой access-row. Длинный диагностический прогон
остановлен; этот промежуточный вариант не выдан пользователю.

В итоговом коде restricted scope имеет parameterized LATERAL CreatorAccount
lookup с OFFSET 0 как барьером разворачивания подзапроса. Сортировочный ключ
берётся из x.creatorId; cursor ограничивает сам индекс назначений. Для страницы
из текущего authority выбирается broad или restricted ветка, причём SQL всё
равно проверяет m.broad — входной hint не может расширить доступ. Billing lookup
также ограничен одной записью по creatorId до проверки дат. Не добавлены
глобальные блокировки или копии каталога. Используются существующие индексы.

Проверен полный обход без предварительного ANALYZE и отдельный forced-index
EXPLAIN после ANALYZE. Forced-index диагностика доказывает доступность пути,
не гарантирует production planner choice/latency. Старый неудачный план
сохранён в initial-statistics-plan.log как инженерное свидетельство.

2.5. Durable MEMBER_CURRENT refresh intent

Home refresh сохраняет один demand scopeMode=MEMBER_CURRENT, creatorIds=NULL,
requestedByMemberId/requestedAccessEpoch. Identity включает member + epoch:
два разных участника больше не коалесцируются в один agency-wide запрос,
перезаписывая происхождение намерения. Повтор того же member/epoch/range
сохраняет прежнюю модель coalescing/requestRevision.

Worker получает membership без JSON списка, SQL выбирает ограниченную READY
страницу. В каждой записи результатов планирования остаётся существующая
атомарная граница jobs+cursor, claimToken, claimed/requestRevision, lease и epoch.
Management commit authority получает узкую opt-in relationalCreatorScope ветку:
Creator/User/Member locks и permission recheck сохранены; bounded targets
сверяются SQL, не полным assignedCreators. Сначала берётся общий billing barrier
Agency, затем Creator/User/Member/demand. Между проверкой core-access и commit
billing writer не может незаметно отозвать разрешение.

LEGACY demand не переосмысляется автоматически: уже сохранённый explicit scope,
lease, cursor и revision сохраняют старый путь до завершения. Это контролируемая
совместимость очереди, а не утверждение, что все потребители allowedCreatorScope
во всём backend переписаны. Исторические reducers Home сохранены только как
__test oracle для старых тестов; новый runtime buildHomeSummary их не вызывает.
Общие legacy consumers и их окончательное удаление — отдельный инвентарь/Phase7.

2.6. Migration and mixed deployment

Новая миграция:
20260929170000_phase6_home_member_scope_v1.
Добавляет scopeMode TEXT NOT NULL DEFAULT LEGACY. Старые миграции не изменены.
CHECK допускает только LEGACY/MEMBER_CURRENT; новый режим не допускает explicit
creatorIds. CHECK созданы NOT VALID: новые/изменённые строки проверяются сразу,
история не сканируется; прежние строки имеют заведомый constant default LEGACY.
Каталожный convalidated для этих двух новых CHECK остаётся false намеренно.
DDL в одной транзакции, lock_timeout 5s; новых индексов и backfill history нет.

DB trigger phase6_home_member_scope_claim_guard запрещает выдачу MEMBER_CURRENT
demand старому worker без transaction-local onlinod.home_member_scope_version=1.
Новый claim устанавливает этот marker в своей существующей root transaction.
Это не секрет/право пользователя, а fence версии исполнения для смешанного
развёртывания. Старые workers могут завершать LEGACY work; попытка взять новый
режим завершится HOME_MEMBER_SCOPE_WORKER_UPGRADE_REQUIRED. Во время rollout
нужно обновить/перезапустить все backend scheduler processes; старые иначе могут
логировать отказ и задерживать обслуживание, но не исполняют новый scope по
старым правилам. Marker не остаётся на pooled connection после commit.

Порядок после закрытия открытых gates: migration + Prisma generate + все Backend
processes, затем совместимый Desktop. Откат одного только Backend на C1 после
появления MEMBER_CURRENT demands не является функциональным rollback Home.
Не удалять новую колонку/намерения ради отката. Нужен отдельный план сохранения
очереди. В этом проходе ни rollout, ни rollback не выполнялся.
