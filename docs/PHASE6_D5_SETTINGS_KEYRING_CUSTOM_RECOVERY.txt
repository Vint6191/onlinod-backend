2. КОРНЕВЫЕ КЛЮЧИ: ПОЛНЫЙ ПУТЬ ДО СОХРАНЕНИЯ RECOVERY CODE

Подтверждённый разрыв D4:
initializeAgencyRoot/beginRootRotation создавали случайные AMK/recovery key,
отправляли серверную запись, затем возвращали код в окно. После успешного
commit и потери HTTP/IPC, закрытия окна или процесса код больше нельзя было
получить через эту операцию. Повтор initialize упирался в already initialized;
повтор rotation сталкивался с другой текущей версией. Серверный owner wrap
позволял восстановить сам AMK, но не потерянный recovery key.
Отдельно старые методы могли вернуть recoveryCode после смены локального
scope: проверка epoch лишь запрещала обновление кеша, но не возврат кода.

D5:
- Новый RootRecoveryJournal хранит один незавершённый корневой intent на
  backend/user/agency/device. Имя файла содержит hash этого scope; содержимое
  целиком защищено Electron safeStorage. Master key, recovery key, operation ID
  и версии не попадают в обычный JSON command journal. Нет передачи AMK/CDK
  в renderer или записи этих ключей в логи.
- Сначала синхронная атомарная запись с fsync, только затем запрос смены root.
  Ошибка диска/OS-хранилища прерывает операцию до корневого HTTP-запроса.
  basic_text backend не допускается для этого журнала.
- Intent закрепляет baseRootVersion, next root и recovery key. При повторе
  используется тот же материал, даже если приходится обновить список owner
  devices или заново сформировать случайные IV/ephemeral wraps.
- Перед решением о повторе читается текущий серверный status. При уже принятой
  версии локальный pinned X25519 key открывает текущий owner wrap; полученный
  AMK сравнивается со staged AMK. Одного равенства номера версии недостаточно.
  Это позволяет восстановить результат без ещё одного root write.
- При не принятом результате существующие серверные initialize/CAS остаются
  владельцами commit. Поздний первый запрос и повтор могут записать только
  одну и ту же staged генерацию. Повтор не создаёт новую генерацию root.
- Только актуальный owner/device получает recoveryCode. Principal, login
  incarnation и keyScopeEpoch проверяются на асинхронных границах. Settings
  дополнительно проверяет текущий CONTROL permit после чтения результата
  и обновления состояния, а также совпадение показанной root version.
- Параллельные одинаковые вызовы в процессе объединяются. Другой корневой
  запуск блокируется до разрешения предыдущего.
- Код сохраняется до явного «I saved it». ACK привязан к предъявленному
  operation ID и актуальному scope. Ошибка записи ACK оставляет возможность
  восстановления. Повтор доставленного ACK в текущем процессе безопасен.
- Удаление записывает защищённую атомарную tombstone. Окно Windows replacement,
  когда остался только .bak, восстанавливается. Повреждённый журнал не
  карантинируется с последующим автоматическим сбросом на пустой.
- Отдельное удаление obsolete setup допускается только после чтения текущего
  owner wrap и подтверждения, что другая неубывающая генерация уже исключает
  поздний commit прежней операции. Неопределённый запрос при прежней root
  version забыть нельзя. Действующий recovery code удаляется через ACK.

В Settings добавлены typed RPC, resume/ACK/discard и явный переход
«Encryption recovery». Ранее соответствующая вкладка отсутствовала в TABS
и не имела доступного перехода. Теперь владелец может вернуться к сохранённой
операции после перезапуска. Карточка указывает версию root и объясняет срок
хранения локальной защищённой копии. Старое обещание «исчезнет после ухода
с экрана» заменено фактическим поведением до подтверждения сохранения.

Ограничения:
- Новая гарантия начинается с операций, подготовленных D5. Уже потерянный
  recovery key старой операции D4 нельзя восстановить из ничего.
- Потеря локального диска/OS keychain остаётся отдельным сценарием: recovery
  code необходимо сохранить вне этого ПК. Полный аппаратный отказ не
  эквивалентен потере HTTP-ответа.
- Настоящий Windows/macOS/Linux keychain и Electron не запускались. Тесты
  используют реальные X25519/HKDF/AES-GCM из исходного crypto-модуля и
  подставленное защищённое safeStorage. Это поведенческое доказательство
  протокола, не подтверждение всех платформенных свойств хранилища.
- Прочие команды keyring/device/creator-key rotation не объявлены целиком
  закрытыми этим исправлением двух корневых операций.

3. SETTINGS: АКТУАЛЬНЫЙ USER И СМЕНА ПАРОЛЯ

D4 проверял текущий пароль bcrypt до транзакции. Затем транзакция брала
authorization-user lock и без сверки записывала новый hash. Два запроса,
проверившие один старый пароль, могли последовательно перезаписать друг друга.
В profile/avatar/password не было общей проверки persistent disabledAt
пользователя непосредственно перед записью.

D5 вводит lockEligibleAccountUser:
- authorization-user advisory lock, затем User FOR UPDATE;
- чтение текущего User, запрет отсутствующего/отключённого пользователя;
- profile/avatar записываются внутри этого владельца;
- bcrypt остаётся снаружи долгой транзакции, но успешная проверка привязана
  к точному исходному passwordHash. Если он сменился — 409
  SETTINGS_PASSWORD_CHANGED, без записи пароля и отзыва сессий;
- при успешной смене сохраняется прежняя политика отзыва остальных сессий.
  Audit использует переданный client, включая изолированные SQL-проверки.

Ни общая exactly-once семантика всех Settings setters, ни почтовые эффекты,
ни идемпотентный retry смены пароля после потерянного ответа здесь не заявлены.
Повтор после успешной смены со старым паролем закономерно требует нового входа;
главная гарантия этого изменения — не перезаписать чужую более новую смену.

4. ПРОКСИ И NETWORK: ГРАНИЦА COMMIT, CAS И СТАРЫЙ МАРШРУТ

D4 повторно читал membership, однако одного SERIALIZABLE snapshot было
недостаточно для общей блокировки с User disable и изменением полномочий.
Особенно это затрагивало metadata-only правки без чтения creator key.
Ответ alreadyDeleted также обходил live management authority.

D5 использует существующий assertManagementCommitAuthority:
Agency lifecycle -> Creator -> User/Member. Проверяются creators.manage,
creator scope, persistent eligibility и admitted accessEpoch; блокировки
держатся до commit. Существующие продуктовые/биллинговые проверки сохраняются.
Проверяется соответствие authenticated user и actor membership. Старые
доменные коды permission/scope отказа сохраняются, добавлен PROXY_ACCESS_STALE.
Даже ответ о ранее удалённом endpoint проверяет текущие права управления.

Сохранены version CAS endpoint/profile, dedicated ownerCreatorId,
CLIENT_E2E_V1 и запрет plaintext credentials на сервере. Unique race при
создании dedicated proxy переводится в 409 после rollback; запросов к
отменённой транзакции нет. SQL повтор creator-bound create с тем же
expectedNetworkVersion не создаёт второго endpoint.

Старое создание не привязанного к creator proxy pool прекращено:
POST /api/network-profiles/proxies для валидного старого запроса возвращает
410 PROXY_POOL_CREATE_RETIRED до записи. Поиск текущих вызовов подтвердил,
что Desktop92 создаёт только через /creators/:creatorId/proxy. Старые
endpoint записи не удаляются; читаются и обрабатываются существующими
версионными путями. Остальные сетевые маршруты не закрывались.

Полный Desktop journal/readback UX для неопределённого результата всех
сетевых действий остаётся открытым. CAS предотвращает дубль/перезапись,
но сам по себе ещё не возвращает пользователю подтверждённую квитанцию.

5. CUSTOM ORDERS: CREATE И READBACK ПОД ОДНИМ ВЛАДЕЛЬЦЕМ

Подтверждено в D4:
- проверка существующего clientMutationId делалась до транзакции и могла
  вернуть результат по прежнему membership без commit-time проверки;
- после P2002 обработчик читал тот же PostgreSQL transaction, уже aborted;
- два допущенных запроса не повторяли lookup после ожидания первого writer.

D5:
Agency lifecycle -> agency/clientMutationId advisory mutex -> Creator lifecycle
-> live User/Member/access -> lookup/create/reminder projection/TASK planning.
Существующие UUID и stableCreateFingerprint не менялись.
Совпавший intent возвращается только после текущей авторизации. Другой payload
или creator с тем же UUID получает конфликт. Ветка чтения после P2002 удалена.
Создание заказа, проекция напоминания и планирование canonical Telegram work
остаются в одном корневом commit; повтор не создаёт эти действия заново.

getCustomOrderByClientMutationId теперь проходит тот же intent owner и текущую
авторизацию. Первое чтение нужно лишь для creator binding; сам заказ заново
читается после блокировки Creator, чтобы не вернуть прежнее состояние после
ожидания параллельного update/cancel.

Сохранены права на ручные поля, ограничения CONTENT provenance/completion,
физическая граница COMMITTING, TASK/REVISION_REQUEST fences и отдельные
settlement/relay/Telegram владельцы. Они не заменялись общим HTTP receipt.
Наличие create UUID не засчитано как закрытие всех Custom subcommands.
