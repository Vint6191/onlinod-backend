3. ВЛАДЕЛЕЦ TELEGRAM CONTROL

POST /api/telegram-control/commands/v1 и /v1/cancel, authRequired, no-store.
Пять строгих действий: telegram.create, telegram.reminders, telegram.retire,
telegram.forceRetire, telegram.session. UUID, target и payload проверяются;
ошибки валидации не возвращают сырые присланные API hash/сессию.
Предел payload — 272 KiB. API ID — положительное целое до2147483647, API hash —
32 hex-символа, сессия — от1 до262144 символов, без молчаливого усечения.
Интервалы напоминаний:1–525600; список offsets:1–12; текст:до2000 символов.
Force требует явного acknowledgment и непустой причины до1000 символов.

Использована существующая таблица ManagementCommandReceipt D6, новой миграции нет.
Отдельное пространство telegram_control_v1_; идентичность включает agency/user/UUID.
Fingerprint учитывает namespace, UUID, действие, target и исходный payload.
Receipt хранит только locator accountId либо пустой reference для reminders.
API hash, MTProto session и зашифрованные credential bytes в receipt не пишутся.

Replay подтверждает уже зафиксированное событие и выдаёт текущий безопасный readback.
Если подключение уже удалено, account:null подтверждает прежнее исполнение;
старый receipt не воссоздаёт аккаунт и не возвращает прежнюю сессию/настройки.
Cancel-before-execute фиксирует ABANDONED; commit-before-cancel подтверждает commit.
Отмена не откатывает уже выполненную запись и не создаёт компенсирующее удаление.

Новое исполнение связано с исходными deviceId и authorizationSessionId из signed
login, добавленными Main. Новый login может подтвердить прежний commit, но не может
выполнить ещё не исполненное намерение старого login. Его можно отменить и создать
новое осознанное действие. Replay/cancel тоже требуют актуальных прав и живого login.

Один kernel root SECRET_WRITE, serializable, maxAttempts1. Порядок:
общий Agency lifecycle barrier -> command advisory lock -> authorization-user lock
-> User FOR UPDATE -> текущие User/Member/epoch и роль OWNER/ADMIN -> живая signed
RefreshSession lineage -> целевые policy/account/count locks -> запись домена,
обязательный audit и receipt. Request-time auth не заменяет commit-time проверку.
Receipt failure/audit failure откатывает доменный эффект в этой же транзакции.

4. ВЕРСИИ И ОГРАНИЧЕННЫЙ READBACK

credentialRevision вычисляется по encrypted bytes/IV/tag/algorithm/version/API ID/id.
Это версия сохранённого ciphertext, не публичный хеш низкоэнтропийного plaintext.
accountRevision включает credentialRevision, lifecycle/retirement и runtime
owner/claim token/claim generation/drain generation. Runtime heartbeat TTL из версии
исключён, чтобы продление lease не ломало редактор; force проверяет TTL по DB clock.

Reminder policy и dependency generation читаются одним SQL LEFT JOIN snapshot;
версия учитывает обе части, поэтому возврат значения A->B->A не обходит CAS.
Ошибка чтения policy больше не маскируется как успешный read defaults.
Account readback не раскрывает apiHash/session/runtime claim token.
Повреждённый ciphertext остаётся видимым с sessionReady:false, чтобы подключение
можно было вывести из эксплуатации; он не превращается в скрытое исчезновение.

Список подключений ограничен128: запрашивается129-я строка для явного отказа
при переполнении, без выдачи усечённого «полного» списка. Create сериализует счётчик
агентства и не создаёт129-е подключение. Это новая явная граница ёмкости;
её пригодность для целевой нагрузки ещё не является SCALE-приёмкой.

5. УДАЛЕНИЕ, DRAIN И АВТОРИЗАЦИОННЫЙ МАТЕРИАЛ

Переиспользованы существующие владельцы blockers, retirement и bounded fanout.
Две прежние части remove теперь могут присоединиться к текущему command root
только при currentCommitContext().tx === переданному client. Проверка препятствует
выдаче произвольного транзакционного клиента за текущий kernel root.
Normal/force retirement, fanout, required audit и receipt атомарны относительно
этой команды. Падение receipt не оставляет отдельно committed retirement.

Проверки lifecycle/runtime generation и деловых blockers сохранены. Начальное
удаление может вернуть RETIRING/drainRequired. После фактического drain действие
Finish removal использует свежую accountRevision и новый UUID. Replay начального
receipt подтверждает первоначальную команду, а не запускает новую работу.
Физический multi-PC drain и независимые PG sessions этим проходом не доказаны.
Протоколы runtime claim/release и внешней Telegram-доставки здесь не переписаны.

У существующего local-material нормализованный purpose=authorize (trim/lowercase)
направлен в новый reader с текущими User/Member/epoch/OWNER-or-ADMIN/live login.
Account row блокируется; нужны ACTIVE и idle/drained runtime. Повторная авторизация
не разрешена при runtime owner, живом lease либо несовпадении claim/drain generation.
Выдаются Main-only apiHash, пустая предыдущая session и credentialRevision.
Commit новой сессии снова проверяет те же условия и expectedCredentialRevision.
Messaging/source/delivery material остаются у прежних специализированных владельцев;
эта ветка local-material не означает закрытие всех его purpose.

7. QR HELPER: DURABLE ПЕРЕДАЧА И ЗАВЕРШЕНИЕ

Main принимает законченную сессию один раз и синхронно сохраняет зашифрованный intent.
Дубликаты/stale helper messages не заменяют первый handoff. Oversize отклоняется.
После подготовки отменяются старые challenge timers. Только после durable prepare
Main посылает helper сообщение auth-session-staged с его ID.

Helper создаёт ожидание подтверждения перед отправкой сессии и ждёт соответствующий
ID перед штатным qr-auth-complete/exit. Ожидание ограничено15 секундами; cancel его
прерывает. Main начинает backend handoff после наблюдаемого выхода helper; сохранён
2-секундный kill backstop. Disconnect helper ограничен прежними1200 ms.
Сбой durable storage останавливает helper без записи на backend и ложного успеха.
При retry отправляется прежняя подготовленная команда; после restart она доступна
в pending panel без прежнего in-memory challenge.

Поздние success/error не превращают CANCELLED в AUTHORIZED и не очищают более новый
challenge. Карта challenges ограничена32 с уборкой завершённых. Settings проверяет
форму материала, пустую прежнюю session и право/происхождение после асинхронного
запуска helper; при изменении authority новый helper отменяется. Stale provenance
records очищаются при новом запуске. Terminal status можно опрашивать повторно.

Локальный Cancel завершает QR-процесс. Уже подготовленная durable-команда остаётся
отдельно восстанавливаемой/отменяемой через pending panel; локальный cancel не обещает
отменить состоявшийся server commit. Crash до получения/подготовки сессии Main не
восстанавливается этим журналом. Exactly-once внешнего Telegram login не заявлен.
